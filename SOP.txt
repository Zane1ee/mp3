STEP 4: SPECIFY USER/TASK DATA AND REPLACEMENT SEMANTICS
------------------------------------------------------------
Actions:
  DATA-U:
    _id: server-generated ObjectId, serialized as a string in JSON.
    name: required string; email: required string, unique across other users.
    pendingTasks: [String], only existing incomplete tasks belonging to this user.
    dateCreated: server time at creation; client input ignored; immutable on PUT.
  DATA-T:
    _id: same server-generated identity behavior as User.
    name: required string; description: String; deadline: valid Date.
    completed: Boolean; assignedUser: String; assignedUserName: String.
    dateCreated: same server-owned behavior as User.
    Required unassigned pair: assignedUser="", assignedUserName="unassigned".
  PROPOSED D4 normalization/defaults:
    - missing pendingTasks -> []; description -> ""; completed -> false;
      assignedUser -> "". Missing assignedUserName is derived from its user,
      or becomes "unassigned". Explicit wrong types/null are not omissions.
    - Trim required name/email outer whitespace and reject empty results.
      Preserve email case. PROPOSED: use a lightweight email address-shape check
      and reject malformed addresses, without DNS checks or an overly restrictive
      regex. Do not add future-only deadlines, length caps or lowercasing rules.
    - Accept valid date strings supported by the declared parser, including
      ordinary date-only values; serialize dates as ISO. Reject invalid dates,
      including invalid calendar components that a parser might silently roll
      forward. Test timezone offsets representing the same instant. Do not
      restrict to future deadlines or only one ISO spelling.
    - Reference IDs are valid ObjectId-format strings, stored as strings in
      pendingTasks/assignedUser. Normalize equivalent hex spelling and deduplicate
      pendingTasks while preserving first occurrence. Never auto-populate these
      fields with full documents or change their API type to embedded objects.
    - Only mapped business fields are writable. Ignore client _id, dateCreated,
      __v and unknown body properties; never pass req.body as a Mongo update.
  PUT is full business-field replacement, not PATCH and not upsert. Both required
  fields must be supplied again. Apply optional defaults explicitly rather than
  allowing omitted paths to retain old values. Retain _id/dateCreated.
  Deleting a user unassigns their tasks; it does not delete those task documents.
Test / review:
  - Table-test omission vs null/wrong type, creation defaults, immutable dates,
    duplicate email, duplicate references, own-email retention and full PUT.
Acceptance:
  - Contract records each field's ownership, type and default. Proposed details

STEP 5: FREEZE ROUTES, RESPONSES, AND VALIDATION ORDER
------------------------------------------------------------
Actions:
  HTTP-01 GET    /api/users      -> 200, data: array or number with count=true.
  HTTP-02 POST   /api/users      -> 201, data: created user.
  HTTP-03 GET    /api/users/:id  -> 200, data: user; nonexistent/invalid id 404.
  HTTP-04 PUT    /api/users/:id  -> 200, data: updated user; missing target 404.
  HTTP-05 DELETE /api/users/:id  -> D6 success policy; missing target 404.
  HTTP-06 GET    /api/tasks      -> 200, data: array or number with count=true.
  HTTP-07 POST   /api/tasks      -> 201, data: created task.
  HTTP-08 GET    /api/tasks/:id  -> 200, data: task; nonexistent/invalid id 404.
  HTTP-09 PUT    /api/tasks/:id  -> 200, data: updated task; missing target 404.
  HTTP-10 DELETE /api/tasks/:id  -> D6 success policy; missing target 404.
  - Resource responses use exactly message (human-readable string) and data.
    PROPOSED error data is {}; do not expose stack traces, raw cast/duplicate-key
    text, database paths, credentials, or internal error objects.
  - VALID order for parsable POST/PUT bodies:
      1. Validate URL id/target existence for member routes -> 404.
      2. Validate field types, required values and reference ID formats -> 400.
      3. Check email uniqueness, excluding the current user's id -> 400.
      4. Resolve referenced documents -> 404 if an otherwise valid ID is absent.
      5. Check fetched-state rules: pending task incomplete, assigned name
         matches actual user -> 400.
      6. Execute the complete write transaction; unexpected failure -> 500.
    The completed/name checks require document reads; do not claim to evaluate
    them without resolving references. Cover missing/completed mixed cases.
  - Malformed JSON bodies fail during parsing -> 400 envelope; there is no
    meaningful field-validation order until parsing succeeds. For member GET
    with both invalid/missing target and invalid select, PROPOSED target 404
    first (D5). For irrelevant member query parameters, ignore without parsing.
  - Preserve both existing request body parsers. PROPOSED: JSON requires actual
    JSON types; URL-encoded transport explicitly decodes completed=true/false
    and pendingTasks as a JSON-array string or a parsed array, then uses the
    same strict validator. "false" must never become truthy via Boolean(value).
  - D6 resolved by actual grader feedback on 2026-11-04: successful Task/User
    DELETE awaits the committed mutation, then returns 204 with zero body bytes.
    There is no JSON envelope for this success response. Missing/malformed
    targets and unexpected failures retain JSON 404/500. The earlier 200/JSON
    fallback remains only in historical records, not the current contract.
Test / review:
  - Contract cases include every status, error precedence, parser failures,
    both body encodings and response shape. Verify actual updated, not old, data.
Acceptance:
  - Current contracts, runtime, client parsers and independent HTTP-byte tests
    agree on the grader-confirmed DELETE 204/empty policy; errors remain JSON.

STEP 6: SPECIFY QUERY PARSING AND DATABASE EXECUTION
------------------------------------------------------------
Actions:
  QUERY-01: collection where is a JSON object passed to a Mongoose query.
    Preserve documented operators such as $in; ordinary equality, comparison,
    Boolean and multi-field filters must work. Do not sanitize away valid
    operators or fetch every document to filter in JavaScript.
  QUERY-02: sort is a JSON field/direction object, directions 1 or -1.
  QUERY-03: select is a JSON include/exclude object, values 1 or 0; permit the
    normal _id exception. Invalid mixed projections -> 400, not leaked DB error.
  QUERY-04: skip is a nonnegative integer, default 0. PROPOSED reject fractional,
    negative, nonnumeric, repeated and non-scalar pagination input -> 400.
  QUERY-05: limit is a nonnegative integer. Default tasks=100; users=unlimited.
    PROPOSED explicit limit=0 means unlimited, matching Mongo query semantics;
    do not invent an undocumented maximum or silently clamp requested values.
  QUERY-06: count accepts JSON true/false; parse false as false. Return a number
    in data when true. PROPOSED count means all where-matching documents BEFORE
    skip/limit, independent of sort/select. Validate recognized collection
    parameters first, even when count makes some of them operationally unused.
    README does not fully specify this pagination interaction: D5 must freeze it.
  QUERY-07: any combination of the six recognized parameters must work.
    Decode URL encoding once through the framework, then parse JSON once.
    Invalid recognized JSON/type -> 400. PROPOSED ignore unknown query keys.
  QUERY-08: member GET supports only select. Ignore where/sort/skip/limit/count,
    including malformed values, rather than accidentally filtering out the id.
  QUERY-09: unmatched collection -> 200 with [] or 0; member absent -> 404.
  - Query implementation uses Mongoose find/filter/sort/select/skip/limit and
    countDocuments, not post-query array filtering/slicing/counting.
  - API order without sort is not promised. For deterministic pagination tests,
    provide a unique sort key or explicit tie-breaker; do not assert DB natural
    order. Do not inadvertently exclude _id from internal relationship logic.

  - Test both resources, inclusion/exclusion, $in, combined parameters, invalid
    JSON, count=false, defaults with 101 fixtures, limit=0, empty and member cases.
  - Review emitted query construction as well as HTTP results: output alone

  - One shared parser/query builder implements the frozen D5 policy; list vs

STEP 7: DEFINE RELATIONSHIP INVARIANTS AND ATOMICITY
------------------------------------------------------------
Actions:
  REF-01: every incomplete assigned task occurs exactly once in its user's
    pendingTasks; every pendingTasks entry points to that same incomplete task.
  REF-02: completed tasks occur in no pendingTasks but may stay assigned.
  REF-03: task assignedUserName equals the current assigned user's name, even
    for completed tasks; an unassigned task always has the required empty pair.
  REF-04: no reference points to a missing user/task; at most one user owns a
    task. Moving a task owned by another user is valid and removes old ownership.
  REF-05: User POST with pendingTasks and Task POST with assignedUser follow
    the same synchronization rules as their corresponding replacements.
  - User PUT: compare old/new pending IDs. Removed -> unassign; new -> assign
    and remove from any previous user's pending list. Retained pending tasks
    remain assigned. Completed tasks already assigned remain assigned despite
    being absent from pendingTasks. Renaming updates ALL assigned tasks.
  - Task PUT: remove from former user's pending list; add to the requested
    user's list iff incomplete; completed assignments remain valid; reopening
    restores membership; omitted assignment resets to unassigned on replacement.
  - Task DELETE removes pending membership; User DELETE queries all tasks by
    assignedUser, including completed tasks, and unassigns them before deletion.
  ATOM-01: rejected/failed writes change no resource or relationship documents.
  PROPOSED D2 mechanism:
    - Use a single shared transaction service. Re-read relevant state, check
      referenced existence/email and compute differences inside the transaction.
      Any target precheck outside it must be repeated where state can change.
    - Every participating read/write carries the same session. Execute DB
      operations sequentially inside a session; no Promise.all or nested
      transaction. End sessions in all paths; send success only after commit.
    - Retry supported transient conflicts by recomputing from current state.
      No HTTP response, external side effect, or stale change-set replay inside
      a retryable transaction callback. Bound failure handling and return safe 500.
    - Transactions alone do not excuse stale-read races. Ensure all related
      mutations conflict on shared user/task documents using persisted version
      guards (existing internal __v or an equivalent reviewed mechanism).
      Guard/touch the assigned user even for completed-task assignment, where
      pendingTasks may not change, to coordinate with concurrent rename/delete.
      Do not rely on process-local locks or no-op updates as a complete solution.
    - Enforce email uniqueness with a real unique index and map duplicate-key
      races to 400. A pre-query or unique schema option alone is not sufficient.
Test / review:
  - Run an invariant checker after every successful mutation; compare normalized
    before/after snapshots after every rejected request and injected failure.
  - Race same-task transfers, two tasks assigned to one user, rename/assignment,
    completion/transfer and user deletion/completed-task assignment. Verify
    serializable final business outcomes, no lost membership or dangling IDs.
Acceptance:
  - One centralized design covers every POST/PUT/DELETE and failure path. The
    owner approves the transaction dependency; actual atomicity is proved later.
